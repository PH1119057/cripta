## 4. Канон / HARD_STOP
Решение владельца задаёт намерение, но не меняет канон молча. Конфликт: `CANON_CONFLICT=YES`, `HARD_STOP=YES`, `CANON_UPDATE_REQUIRED=YES`, `OWNER_DECISION_REQUIRED=YES`; назвать конфликт и canonical change.
После решения: `CANON UPDATE → IMPLEMENTATION → TEST → GITHUB → DEPLOY → RUNTIME EVIDENCE`.
Код ≠ канон → `FINDING`, без самостоятельной смены кода/архитектуры. Перенос capability: BEFORE/AFTER owner/consumer, без replacement — HARD_STOP + OWNER_DECISION_REQUIRED.
Нет термина в GLOSSARY или физическая неоднозначность: `TERM_AMBIGUOUS=YES`, HARD_STOP + OWNER_DECISION_REQUIRED. Не домысливать.

## 5. Research
Историческое research — evidence, не канон. Не переносить старые Entry/Exit, thresholds, horizons, filters, Strategy parameters/defaults; dataset reuse ≠ policy reuse.
Торговое изменение: `RESEARCH/EVIDENCE → OWNER DECISION → CANON/NEW STRATEGY VERSION → TEST/SHADOW → LIVE EQUIVALENCE → MICRO_LIVE → LIVE`.

## 6. Архитектура
Owner/consumer — ARCH/TRADING_CONTOUR/OBSERVATION_ANALYTICS/GLOSSARY/MAP, архитектуру не дублировать. Перед чувствительной работой проверить актуальный GitHub main, base и routed docs. Research writes только на data-disk; runtime не зависит напрямую от research artifacts.
Patch/deploy не включает LIVE молча; re-arm — current LIVE-arm contract + explicit owner approval.
Real execution smoke — только owner-triggered diagnostic по TC §4.8 / ARCH §7.1, не Strategy. PAPER/REAL: ARCH §7.2, TC §4.9, GLOSSARY §11. R1 SL/TP — TC.
Dashboard read-only UI/read-model отдельно от trading runtime; restart — только Dashboard backend. Auth/control/mutation — full release.

## 7. Отказы, actor и права
Отказы: DEVELOPMENT_RELEASE §19.5–19.6, MAP §1.4; research — RESEARCH_COMPUTE, коммуникация — CHATGPT_INTERACTION_RULES §11.1. Различать OpenAI upstream tool-security block, SentinelX `command_not_allowed`, Unix `EACCES` (actor/path), job timeout (исход неизвестен), GitHub error.
Не выдумывать OpenAI policy. Проверять точный SentinelX allowlist-префикс (`git` ≠ `sudo -u cripta git`); UI full access ≠ unrestricted exec. Owner «повтори» — одна попытка только если tool допускает; не обходить через actor/tool/transport, не просить restart без evidence. `cripta` — read/research actor, `sentinelx` — rail управления; сначала разрешённый smoke, затем bounded run и source/result/QC в GitHub.
Server-side script до подготовки: exact actor/path/owner/group/mode/ACL/systemd sandbox, операции READ/WRITE/CREATE/RENAME/DELETE и parent permissions; проверять от actual writer. Без контракта `PREPARED=NO`. `ReadWritePaths=` ≠ Unix write. Root/SentinelX ≠ writer. Запрещены `chmod 777`, uncontrolled recursive chown/chmod, запуск всего workflow от root и лишние privileges. Server/DB: actor, tool и owner approval — отдельные gates.

## 13. Контроль длительных задач
Для server research/replay/jobs и иных долгих операций:
1. До запуска: `PREPARED`, exact actor/path/контракт, проверить канал уведомлений. Только после подтверждения сервера указать job ID, параметры, место результата и `RUNNING`. Без подтверждения не говорить «запущено».
2. `notify_*` — лишь при работающей интеграции. Push без подтверждения не обещать. Если push недоступен, по возможности создать и подтвердить одноразовый контроль ChatGPT через ~5–10 минут. Повторные проверки не чаще раза в час; для частых — серверные события.
3. Получать фактический job status. `RUNNING` → сообщить и организовать допустимую следующую проверку; `COMPLETED` → проверить результат/QC/parity; `FAILED`/`BLOCKED`/timeout/unknown → назвать класс отказа и выполненную часть. Старые цифры не выдавать за свежие.
4. Отказ в запуске: `NOT STARTED/BLOCKED`, без ожидания несуществующего job и обхода security. Не требовать «?» для первого статуса; без notification/automation инициативное сообщение не обещать.
5. Автоматизация привязана к job ID, прекращается после финального состояния; бесконечный polling запрещён. Различать server push и плановую задачу ChatGPT.

Точное безопасное совпадение → продолжить; неоднозначность → HARD_STOP для mutation + owner decision. Не создавать дубликат и не делать reset/force cleanup.
Checkpoint уборки: MAP §38, INDEX §52, Issue #153. Исторические worktrees не блокируют новые scoped задачи; DEV §50.4 обязателен, historical policy ≠ current.
