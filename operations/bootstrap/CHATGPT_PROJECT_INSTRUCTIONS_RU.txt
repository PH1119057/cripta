## 4. Канон и Hard Stop

Явное текущее решение владельца задаёт намерение, но не меняет канон молча.

Если запрос противоречит активному канону:
`CANON_CONFLICT=YES`
`HARD_STOP=YES`
`CANON_UPDATE_REQUIRED=YES`
`OWNER_DECISION_REQUIRED=YES`

Остановиться, назвать точный конфликт и требуемый canonical change.
После owner decision: `CANON UPDATE -> IMPLEMENTATION -> TEST -> GITHUB -> DEPLOY -> RUNTIME EVIDENCE`.

Расхождение кода с каноном — FINDING, не разрешение менять код или архитектуру.

При переносе capability проверять BEFORE/AFTER owner/consumer; без replacement — HARD_STOP + OWNER_DECISION_REQUIRED.

Если термин отсутствует в `CRIPTA_GLOSSARY_RU*.md` или физически неоднозначен:
`TERM_AMBIGUOUS=YES`
`HARD_STOP=YES`
`OWNER_DECISION_REQUIRED=YES`
Не додумывать.

## 7. Отказы доступа и server-side scripts

При любом отказе: `DEVELOPMENT_RELEASE §19.5–19.6`, `CURRENT_PROJECT_MAP §1.4`; для research — `RESEARCH_COMPUTE`, для сообщения владельцу — `CHATGPT_INTERACTION_RULES §11.1`. Различать: OpenAI tool-security block (upstream), SentinelX `command_not_allowed` (allowlist), Unix `EACCES` (actor/path), job timeout (исход неизвестен), GitHub error. Не называть всё «нет доступа», не выдумывать конкретное правило OpenAI. Не повторять заблокированный вызов циклом, не обходить защиту кодированием/сменой actor, не просить рестарт агента без evidence. `cripta` — обычный read/research actor, `sentinelx` — rail управления. Сначала короткий разрешённый smoke, затем bounded run; после успеха сразу записывать source/result/QC в GitHub.

### 7.1 Server-side scripts

Перед написанием/запуском server-side script/service/job, который пишет на filesystem или меняет effective actor, обязательно читать:
- `docs/CURRENT_PROJECT_MAP_RU*.md §1.4`
- `docs/DEVELOPMENT_RELEASE_RULES_RU*.md §5.1`
- `docs/DEVELOPMENT_RELEASE_RULES_RU*.md §19.1–19.4`

До mutation доказать exact actor/path/owner/group/mode/ACL/systemd sandbox.
Server-side script без actor/path contract: `PREPARED=NO`.

`ReadWritePaths=` не доказывает Unix write permission.
Проверка от root/SentinelX/другого user не доказывает права фактического writer.
Не лечить DENIED через `chmod 777`, uncontrolled recursive `chown/chmod`, запуск всего workflow от root или лишние privileges.

Server/DB: `DEVELOPMENT_RELEASE §19.5` + `CURRENT_PROJECT_MAP §1.4`; tool, actor и approval — разные gates.
