# Постановка задачи: торговая подсистема исполнения стратегий для Bybit

> Исторический документ. Решение по средам исполнения заменено Mainnet-first моделью
> `SHADOW` / `MICRO_LIVE` / `LIVE`, описанной в
> `CODEX_NEXT_TASK_STRATEGIES_AND_BACKTEST.md`. Testnet не входит в critical path.

Статус документа: черновик v0.1. Это рабочие правила и границы первой версии, а не неизменяемый контракт. Их можно расширять и пересматривать по мере появления алгоритмов и результатов испытаний.

## 1. Задача для Codex

Создать локальное Windows-приложение с понятным графическим интерфейсом, которое подключается к Bybit, показывает рынок и состояние счёта, исполняет подключаемые торговые стратегии и независимо контролирует риски, заявки, позиции, обычные стопы и скользящие стоп-полосы.

Сейчас не требуется придумывать «прибыльную» торговую стратегию. Нужно построить безопасный, тестируемый каркас, куда позднее будут подключены **Алгоритм 1** и, возможно, **Алгоритм 2**. До их получения приложение должно уметь работать с ручным тестовым сигналом и демонстрационной стратегией, которая проверяет инфраструктуру, но не позиционируется как торговая рекомендация.

Рабочее название: **Bybit Strategy Workbench**. Название временное.

Главная архитектурная граница:

> Стратегия формирует торговое намерение. Риск-контур решает, допустимо ли оно. Исполнитель превращает разрешённое намерение в биржевые заявки. Только адаптер Bybit имеет право обращаться к бирже.

## 2. Цель первой версии

Получить вертикальный срез, на котором можно безопасно проверить весь путь:

1. получить рыночные данные;
2. сформировать ручной или тестовый сигнал;
3. рассчитать размер позиции и защитные уровни;
4. показать предполагаемую сделку на графике;
5. пропустить её через риск-проверки;
6. отправить заявку в Bybit testnet;
7. подтвердить её состояние по приватному WebSocket;
8. поставить и проверить жёсткий стоп и/или скользящий стоп;
9. восстановить истинное состояние после разрыва связи или перезапуска;
10. записать полный журнал решений, заявок, исполнений и ошибок.

Первая версия должна быть удобной для одного пользователя, одного аккаунта и одной активной позиции на выбранном инструменте. Мультиаккаунт, портфель из десятков инструментов и высокочастотная торговля пока не нужны.

## 3. Временные предположения

Пока пользователь не уточнил иначе, принять следующие значения по умолчанию:

- биржа: Bybit V5 API;
- первый торговый рынок: USDT perpetual, категория `linear`;
- режим позиции: one-way, `positionIdx=0`;
- маржа: isolated;
- один выбранный символ за один запуск стратегии;
- входы стратегии на закрытых свечах, а не на незавершённой свече;
- рабочая временная зона внутри системы: UTC;
- все денежные и количественные вычисления выполняются через `Decimal`, не через `float`;
- live-торговля выключена по умолчанию и не должна включаться случайно.

Архитектура адаптера должна позволять позднее добавить Bybit Spot, inverse-контракты и другую биржу без переписывания стратегий и риск-контура.

## 4. Режимы работы

Приложение должно явно различать четыре режима. Данные, настройки, ключи и журнал одного режима нельзя незаметно смешивать с другим.

1. **Replay / Simulation** — локальное воспроизведение истории, без приватных ключей и без сетевых заявок.
2. **Bybit Testnet** — основной режим разработки и интеграционных испытаний.
3. **Bybit Demo Trading** — отдельный профиль, потому что demo-аккаунт Bybit не является testnet-аккаунтом.
4. **Live** — отдельный профиль, заблокированный по умолчанию.

Верхняя панель интерфейса всегда показывает крупный цветной бейдж текущего режима. Для Live нужны одновременно:

- настройка `allow_live_trading=true` вне интерфейса;
- отдельный live-профиль ключей;
- ручной ввод слова `LIVE` при вооружении стратегии;
- подтверждение символа, максимального размера позиции и дневного лимита убытка;
- отсутствие критических ошибок синхронизации.

Запуск приложения никогда не должен автоматически возобновлять создание новых live-позиций. После перезапуска допускается только синхронизация и сопровождение уже существующей позиции; для новых входов требуется повторное ручное вооружение.

## 5. Предлагаемый стек

Для первой версии использовать стек, удобный для быстрой разработки и последующего подключения математических алгоритмов:

- Python 3.12+;
- PySide6 для Windows GUI;
- `asyncio` + `qasync` для совместной работы интерфейса и асинхронных потоков;
- `pyqtgraph` для свечного графика, уровней и стоп-полос;
- официальный Python SDK Bybit `pybit`, но только внутри адаптера Bybit;
- Pydantic v2 для проверяемых настроек и DTO на границе системы;
- SQLite в режиме WAL + SQLAlchemy 2.x для локального журнала;
- `keyring` / Windows Credential Manager для секретов;
- `pytest`, `pytest-asyncio`, Hypothesis для критических расчётов;
- Ruff и mypy;
- `uv` и `pyproject.toml` для зависимостей;
- PyInstaller для сборки Windows-приложения.

Если в существующем репозитории уже принят другой сопоставимый стек, сначала описать конфликт и предложить минимальный путь интеграции, а не создавать второй независимый стек.

## 6. Архитектура

Разделить код минимум на следующие слои:

```text
src/bybit_workbench/
  app/                 # запуск, жизненный цикл, композиция зависимостей
  domain/              # свечи, сигналы, намерения, заявки, позиции, события
  strategies/          # API стратегий и подключаемые реализации
  risk/                # sizing, лимиты и разрешение/отказ намерений
  stops/               # жёсткие и скользящие стоп-политики
  execution/           # машина состояний заявок и позиций
  exchange/
    base/              # абстрактный интерфейс биржи
    bybit/             # REST/WS, преобразование моделей, rate limiting
    fake/              # детерминированная тестовая биржа
  market_data/         # свечи, тикеры, кэш и проверка свежести
  persistence/         # SQLite, миграции, репозитории и журнал событий
  ui/                  # окна, view-model, графики и диалоги
  observability/       # логи, метрики состояния, health checks
tests/
```

GUI не должен содержать торговую логику. Стратегия не должна получать API-ключ, Bybit-клиент или возможность самостоятельно создать заявку.

Источник истины по реальным позициям и заявкам — биржа. Локальная база является журналом и проекцией. При запуске и после каждого переподключения выполняется reconciliation: REST-снимок сравнивается с локальным состоянием, расхождения фиксируются, а новые входы запрещаются до завершения синхронизации.

## 7. Машина состояний приложения

Ввести явные состояния:

- `DISCONNECTED` — нет надёжной связи;
- `SYNCING` — загружается и сверяется состояние;
- `READY` — данные актуальны, но торговля не вооружена;
- `ARMED` — параметры проверены, стратегия может начать работу;
- `RUNNING` — стратегия обрабатывает события и может выдавать намерения;
- `PAUSED` — новые входы запрещены, существующая позиция сопровождается;
- `DEGRADED` — часть данных недоступна; новые входы запрещены;
- `ERROR` — требуется вмешательство;
- `EMERGENCY_STOP` — новые действия стратегии запрещены, выполняется выбранная аварийная процедура.

Переходы должны журналироваться с причиной. Не допускается переход из `DISCONNECTED`, `SYNCING`, `DEGRADED` или `ERROR` прямо в создание новой позиции.

## 8. Интерфейс стратегии

Определить версионируемый `Strategy` Protocol/ABC. Пример смыслового контракта:

```python
class Strategy(Protocol):
    def metadata(self) -> StrategyMetadata: ...
    def required_data(self) -> DataRequirements: ...
    def default_parameters(self) -> Mapping[str, object]: ...
    async def on_start(self, context: ReadOnlyStrategyContext) -> None: ...
    async def on_bar_closed(
        self,
        context: ReadOnlyStrategyContext,
        bar: Candle,
    ) -> Sequence[TradeIntent]: ...
    async def on_execution(
        self,
        context: ReadOnlyStrategyContext,
        execution: Execution,
    ) -> Sequence[TradeIntent]: ...
    async def on_stop(self, reason: StopReason) -> None: ...
```

Начальный набор намерений:

- `EnterIntent` — направление, логика входа, уровень отмены идеи, предлагаемая стоп-политика, необязательный take-profit;
- `ExitIntent` — закрыть всю позицию или разрешённую долю;
- `UpdateProtectionIntent` — сдвинуть стоп или take-profit;
- `CancelEntryIntent` — отменить ещё не исполненный вход;
- `NoOp` — явное отсутствие действия с диагностической причиной.

Стратегия не задаёт окончательный биржевой объём без проверки. Риск-контур рассчитывает или ограничивает количество на основании стоп-дистанции, доступного капитала, шага количества, минимального номинала, плеча и глобальных лимитов.

Каждый запуск хранит:

- идентификатор и версию стратегии;
- снимок параметров;
- версию кода/commit hash, если доступен;
- режим работы и символ;
- входные данные, по которым принято решение;
- созданные намерения и решения риск-контура.

Зарезервировать точки подключения `user_algorithm_1` и `user_algorithm_2`, но не выдумывать за пользователя их правила. До получения описания алгоритмов использовать только `ManualProtectedTrade`, который создаёт ручной тестовый сигнал и проверяет всю цепочку исполнения.

## 9. Риск-контур

Риск-контур обязан работать независимо от стратегии и запрещать действие при неопределённости. Минимальные настройки:

- максимальный риск на сделку в валюте счёта и/или процентах equity;
- максимальный номинал позиции;
- максимальное разрешённое плечо;
- максимальный суммарный дневной убыток;
- максимальная серия убыточных сделок;
- максимум открытых позиций и незавершённых входных заявок;
- допустимое проскальзывание;
- минимальная дистанция до ликвидации;
- cooldown после закрытия позиции и после ошибки;
- максимальный возраст рыночных данных;
- максимальное время отсутствия приватного WebSocket;
- разрешённые символы, направления и часы работы;
- запрет усреднения и мартингейла по умолчанию;
- запрет увеличения позиции, если защитный стоп не подтверждён.

Перед заявкой проверить ограничения инструмента, полученные из `instruments-info`: tick size, qty step, минимальное количество/номинал и ценовые ограничения. Все цены и количества округляются осознанно в безопасную сторону и журналируются до и после нормализации.

Любой выход из позиции должен использовать `reduceOnly`, где это применимо. Повторная отправка команды не должна случайно открыть противоположную позицию.

## 10. Жёсткие и скользящие стоп-полосы

Термин **стоп-полоса** в первой версии означает одновременно доменную защитную границу и её визуальную зону на графике. Точная формула пользовательских полос будет задана вместе с Алгоритмом 1/2.

Поддержать следующие базовые политики:

1. `FixedPriceStop` — конкретная цена.
2. `PercentStop` — расстояние в процентах от входа или опорной цены.
3. `DistanceStop` — абсолютная дистанция цены.
4. `ATRStop` — расстояние как множитель ATR; используется только как инфраструктурный примитив, не как готовая торговая стратегия.
5. `TrailingDistanceStop` — биржевой trailing stop по дистанции с необязательной ценой активации.
6. `TrailingPercentStop` — клиентская скользящая полоса в процентах.
7. `CustomStopPolicy` — интерфейс для формулы будущего алгоритма.

Правила безопасности:

- у long-позиции обычный или trailing stop без специальной команды может двигаться только вверх;
- у short-позиции — только вниз;
- расширение риска требует отдельного явного разрешения и подтверждения в UI;
- UI показывает planned, requested и exchange-confirmed уровни разными стилями;
- после входа исполнитель обязан подтвердить наличие защиты через приватные события и/или REST;
- если защита не подтверждается за ограниченное время, новые действия блокируются и запускается настроенная процедура: повторная постановка, пауза либо аварийное закрытие;
- частичные исполнения корректируют защищаемое количество;
- при полном закрытии связанные защитные заявки должны исчезнуть или быть отменены;
- обновления клиентского trailing stop дедуплицируются, ограничиваются по частоте и не отправляются при несущественном изменении меньше tick size;
- при потере приложения биржевая защитная заявка должна продолжать существовать, поэтому для реальной позиции предпочтителен exchange-native stop; клиентская полоса может дополнять, но не заменять минимальную серверную защиту.

На графике отображать:

- цену входа;
- среднюю фактическую цену;
- жёсткий стоп и заштрихованную риск-зону;
- скользящую стоп-полосу и историю её движения;
- take-profit, если есть;
- mark price и liquidation price для деривативов;
- planned/requested/confirmed состояние каждого уровня;
- ожидаемый убыток до стопа с учётом комиссии и заданного проскальзывания.

Разрешить перетаскивание планируемого стопа мышью до входа. Для изменения подтверждённого стопа действующей позиции требуется диалог с новой суммой риска; молчаливое расширение стопа запрещено.

## 11. Интеграция с Bybit

Использовать V5 API и держать все специфические поля внутри `exchange/bybit`.

REST использовать для:

- первичных и контрольных снимков счёта;
- account info и margin mode;
- instrument metadata;
- fee rate;
- исторических свечей;
- открытых заявок, позиций и истории при reconciliation;
- создания/изменения/отмены заявки, если не выбран торговый WebSocket;
- постановки и проверки TP/SL/trailing stop.

WebSocket использовать для:

- публичных свечей, тикера и при необходимости order book;
- приватных `order`, `execution`, `position`, `wallet`;
- подтверждения асинхронно принятой команды создания заявки.

Bybit сообщает только о принятии запроса на создание заявки; окончательное состояние нужно подтверждать через WebSocket. Поэтому исполнитель должен иметь идемпотентный `orderLinkId`, машину состояний и таймаут reconciliation, а не считать HTTP `200/retCode=0` исполненной сделкой.

Обязательная устойчивость:

- heartbeat и контроль возраста последнего сообщения;
- reconnect с exponential backoff и jitter;
- восстановление подписок;
- REST reconciliation после reconnect;
- дедупликация по `orderId`, `orderLinkId`, `execId` и версии/времени события;
- корректная обработка частичных исполнений и нескольких executions в одном сообщении;
- обработка сообщений вне ожидаемого порядка;
- общий rate limiter с запасом относительно лимитов Bybit;
- реакция на clock skew, auth error, rate limit, symbol halt и insufficient margin;
- конфигурируемый API-домен с учётом региональных доменов Bybit, без жёсткой привязки только к `api.bybit.com`.

## 12. Главный экран

Собрать один понятный рабочий экран без лишних окон.

### Верхняя строка

- режим: Replay / Testnet / Demo / Live;
- состояние подключения Public WS, Private WS и REST;
- состояние движка;
- equity, available balance и дневной PnL;
- кнопки `Пауза`, `Запретить новые входы`, `Аварийные действия`.

### Левая панель

- символ и категория рынка;
- таймфрейм;
- выбор стратегии;
- параметры стратегии;
- профиль риска;
- кнопки `Проверить`, `Вооружить`, `Запустить`, `Остановить`.

### Центр

- свечной график;
- индикаторы, запрошенные стратегией;
- вход, стопы, скользящие полосы, take-profit и liquidation price;
- визуальный предпросмотр позиции до отправки.

### Правая панель

- предлагаемое направление и причина сигнала;
- предполагаемый entry, stop, distance и размер;
- риск в валюте и процентах equity;
- комиссия, funding-информация и оценка проскальзывания;
- результат каждой риск-проверки;
- planned/requested/confirmed уровни защиты.

### Нижние вкладки

- Positions;
- Orders;
- Executions;
- Strategy decisions;
- Risk events;
- System log.

Критическая ошибка должна быть видна обычному пользователю, а не только записана в файл лога. Сообщение должно отвечать на три вопроса: что произошло, что система сделала автоматически и что требуется от пользователя.

## 13. Аварийные действия

Не объединять все действия в одну неоднозначную красную кнопку. Предусмотреть отдельные операции с явным предпросмотром последствий:

1. **Pause strategy** — запретить новые намерения, продолжать защиту позиции.
2. **Cancel entry orders** — отменить только незаполненные входные заявки.
3. **Cancel all non-protective orders** — сохранить подтверждённые защитные стопы.
4. **Flatten position** — закрыть позицию reduce-only рыночной или агрессивной лимитной заявкой; требует отдельного подтверждения.
5. **Emergency stop** — запретить новые входы, отменить входные заявки и выполнить заранее выбранную политику по позиции.

Каждое аварийное действие идемпотентно, сохраняет журнал и после выполнения запускает reconciliation.

## 14. Replay и симуляция

Сделать простой детерминированный движок воспроизведения свечей. Он нужен для проверки Алгоритма 1/2 до testnet, но его результаты нельзя выдавать за точное моделирование рынка.

Минимальные правила симуляции:

- стратегия получает только те данные, которые были доступны в моделируемый момент;
- запрет look-ahead bias;
- рыночная заявка исполняется по следующей доступной цене с настраиваемым проскальзыванием и комиссией;
- лимитная заявка считается исполненной только при пересечении её цены;
- gap через стоп исполняется по первой доступной цене, а не по идеальной stop price;
- если внутри одной свечи пересечены и stop, и take-profit и порядок неизвестен, использовать консервативный сценарий либо помечать результат как ambiguous;
- funding и комиссии учитываются отдельно, если данные доступны;
- одинаковые данные и seed дают одинаковый результат.

Сразу показать пользователю ограничения candle-based replay: без тиков нельзя достоверно восстановить внутрисвечной порядок событий и реальную очередь лимитной заявки.

## 15. Хранение и журнал

Минимальные сущности SQLite:

- `strategy_runs`;
- `strategy_decisions`;
- `trade_intents`;
- `risk_decisions`;
- `orders` и история их состояний;
- `executions`;
- `position_snapshots`;
- `stop_updates`;
- `reconciliation_runs`;
- `system_events`;
- `settings_versions`.

Журнал должен позволить восстановить цепочку:

> входные данные → решение стратегии → намерение → риск-проверки → нормализованная заявка → ответ Bybit → executions → позиция → изменения стопов → выход.

Секреты, подписи запросов, полные API-ключи и чувствительные заголовки никогда не сохраняются в логе. Для разработки предоставить `.env.example` без реальных значений; рабочие ключи хранить в Windows Credential Manager.

API-ключ для торговли должен иметь только необходимые торговые и read-права. Withdrawal-права не требуются и не должны запрашиваться.

## 16. Тесты

### Unit

- округление цены и количества;
- sizing по расстоянию до стопа;
- все глобальные лимиты риска;
- монотонность trailing stop для long/short;
- запрет расширения риска;
- stale-data guard;
- дневной loss limit и cooldown;
- идемпотентность аварийных команд.

### Property-based

- стоп long никогда самопроизвольно не снижается;
- стоп short никогда самопроизвольно не повышается;
- разрешённый размер не превышает заданный риск с учётом округления;
- exit/reduce-only не увеличивает абсолютную позицию.

### Integration через FakeExchange

- полное исполнение;
- частичное исполнение;
- отклонённая заявка;
- duplicate/out-of-order WS event;
- disconnect сразу после принятия команды;
- reconnect и reconciliation;
- отказ постановки стопа;
- gap через стоп;
- перезапуск приложения при открытой позиции;
- rate limit и clock skew.

### Bybit testnet

Тесты с реальной сетью должны быть отдельными, выключенными по умолчанию и никогда не использовать live-профиль. Нужен smoke-сценарий: маленькая testnet-позиция, подтверждённый stop, изменение trailing stop, закрытие и финальная сверка нулевой позиции.

## 17. Этапы реализации

Codex должен двигаться маленькими проверяемыми вертикальными срезами, а не писать весь проект одним большим блоком.

### Этап C — риск и стоп-движок в симуляции

Результат: техническая возможность подготовлена, но реальная торговля не выполняется без отдельного явного решения пользователя.

### Этап G — Алгоритм 1 и Алгоритм 2

Не начинать до получения от пользователя формальных правил. Для каждого алгоритма сначала оформить:

- входные данные и таймфреймы;
- точные условия входа/отмены/выхода;
- работу на незакрытой или только закрытой свече;
- sizing;
- начальную стоп-полосу;
- формулу и частоту движения скользящей полосы;
- take-profit и частичные выходы;
- повторный вход и cooldown;
- поведение при пропуске данных и перезапуске;
- набор воспроизводимых примеров и контрпримеров.

Только после согласования этих правил писать реализацию и golden tests.

## 18. Критерии приёмки стартовой подсистемы

Первая стартовая подсистема считается готовой, когда:

- запускается на чистой Windows-машине по документированной инструкции;
- может работать полностью офлайн через FakeExchange;
- подключается к Bybit testnet и отображает согласованные balance/orders/position;
- никогда не торгует в Live по умолчанию;
- ручной тестовый вход проходит risk gate;
- заявка имеет идемпотентный идентификатор и подтверждается по WebSocket;
- жёсткий стоп виден как planned/requested/confirmed;
- trailing stop двигается только в сторону уменьшения риска;
- при disconnect запрещаются новые входы;
- после reconnect или перезапуска состояние сверяется с биржей;
- аварийное закрытие не может открыть обратную позицию;
- все критические сценарии FakeExchange покрыты автоматическими тестами;
- секреты отсутствуют в БД, логах и репозитории;
- пользователь может понять текущее состояние без чтения исходного кода.

## 19. Что не входит в первую версию

- обещания доходности;
- оптимизатор, автоматически подгоняющий стратегию под историю;
- машинное обучение и LLM в контуре принятия торгового решения;
- HFT, арбитраж с микросекундными требованиями;
- одновременная торговля множеством аккаунтов;
- копитрейдинг;
- автоматические вводы и выводы средств;
- хранение withdrawal API key;
- DEX и межсетевые мосты;
- облачный сервер и удалённое управление через интернет;
- окончательная реализация Алгоритма 1/2 до формализации правил.

## 20. Правила работы Codex

1. Сначала прочитать репозиторий, `AGENTS.md` и существующие соглашения.
2. Сверить актуальные поля и ограничения с официальной документацией Bybit V5; не полагаться на память.
3. Перед кодированием выдать короткий поэтапный план и список временных предположений.
4. Не блокировать фундамент из-за ещё не полученных Алгоритмов 1/2.
5. Не подменять отсутствующие торговые правила собственной «прибыльной» логикой.
6. После каждого этапа запускать релевантные тесты и показывать результат.
7. Не оставлять критическую безопасность как TODO перед переходом к следующему торговому режиму.
8. При неоднозначности выбирать fail-closed: запретить новый вход, сохранить защиту, показать причину.
9. Не обращаться к live endpoint и не отправлять реальную заявку без отдельного разрешения пользователя в текущей задаче.
10. Документировать известные ограничения и решения, особенно расхождения локального и биржевого состояния.
