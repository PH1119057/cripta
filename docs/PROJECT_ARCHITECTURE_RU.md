# АРХИТЕКТУРА ПРОЕКТА «КРИПТА»

**Документ:** `PROJECT_ARCHITECTURE_RU.md`  
**Версия:** 1.0  
**Статус:** глобальный архитектурный контракт  
**Назначение:** определить роли основных слоёв торгового комплекса, допустимые связи между ними и обязательный статистический след для развития системы.

---

## Уточнение V1.2: общий рынок, геометрия входа и владение

Маяк публикует один неизменяемый снимок внешнего рынка `SharedMarketContext`.
Он не содержит торговой команды. Диспетчер создаёт отдельные оценки пригодности
для профилей стратегий, поэтому один `market_context_id` может дать разным
стратегиям разные решения. Общий рыночный контекст не является командой
`закрыть всё`; глобальный выход допустим только как отдельная техническая
аварийная защита биржевого контура.

В момент сигнала Entry сохраняется неизменяемая геометрия: точные границы зон,
их роли, времена закрытия исходных свечей, версия расчёта и fingerprint
конфигурации. Связь `signal_id -> entry_command_id -> execution IDs ->
position_id` сохраняется явно. После фактического исполнения Entry больше не
владеет позицией, а Supervisor, Exit и Аналитик используют стабильный
`position_id` и `trade_id`; восстановление владения по одной монете и близкому
времени запрещено как неоднозначное.

Полный фактический чистый результат называется `actual_net_pnl` только при
наличии всех применимых расходов, включая funding. Пока funding отсутствует,
хранится отдельный `actual_net_without_funding`, а полнота равна
`PARTIAL_NO_FUNDING`.

# 1. Главная идея проекта

Проект строится не как один большой торговый бот.

Он состоит из независимых слоёв с разной ответственностью.

Основная цепочка:

```text
ВНЕШНИЙ МИР
     ↓
   МАЯК
     ↓
 ДИСПЕТЧЕР
     ↓
ТОРГОВЫЕ СТРАТЕГИИ
     ↓
ENTRY / RISK / EXECUTION / EXIT
     ↓
   БИРЖА
```

Параллельно:

```text
РЕАЛЬНАЯ ОТКРЫТАЯ ПОЗИЦИЯ
          ↓
 POSITION SUPERVISOR
```

И вокруг всей системы:

```text
ЖУРНАЛЫ + СТАТИСТИКА + RESEARCH
```

Каждый слой имеет собственную ответственность и не должен незаметно подменять другой.

---

# 2. Маяк

## Роль

Маяк — независимый наблюдатель внешнего рынка.

Он отвечает:

> **Что происходит в море?**

Маяк может наблюдать:

- цену;
- реальные сделки;
- спот;
- срочный рынок;
- открытый интерес;
- финансирование;
- стакан;
- ликвидации;
- ширину рынка;
- синхронность;
- BTC/ETH;
- несколько централизованных бирж;
- DEX;
- блокчейн-потоки;
- ожидаемые макроэкономические события;
- политические и регуляторные события;
- фактическую реакцию рынка на них.

Количество источников архитектурно не ограничивается.

## Маяк не торгует

Маяк не имеет права:

- открывать или закрывать сделки;
- блокировать Entry;
- менять Risk;
- двигать stop;
- менять размер позиции;
- менять стратегию;
- учитывать прибыль или убыток конкретной стратегии как признак рынка.

Маяк должен работать одинаково независимо от наличия торговых ботов.

---

# 3. Диспетчер стратегий

## Роль

Диспетчер получает объективный снимок Маяка и отвечает:

> **Для каких типов торговли текущая рыночная среда подходит, а для каких — нет?**

Он является интерпретатором пригодности среды.

Например один и тот же рынок может быть:

- плохим для консервативной стратегии;
- хорошим для пробоя вниз;
- слишком ранним для покупки отскока;
- подходящим для стратегии высокой волатильности.

## Диспетчер не меняет Маяк

Связь:

```text
Маяк → Диспетчер
```

Односторонняя.

Диспетчер не имеет права изменять состояние Маяка.

## Диспетчер не торгует

Он не:

- открывает;
- закрывает;
- изменяет stop;
- изменяет размер;
- изменяет плечо;
- отправляет ордера.

Его результат — только оценка рыночной среды.

---

# 4. Профиль рыночной среды стратегии

Каждая стратегия должна отдельно описывать:

> **какой рынок ей нужен.**

Это не Entry-условия.

Это профиль рабочей среды.

Например стратегия может предпочитать:

- низкую/нормальную волатильность;
- отсутствие развивающегося ликвидационного каскада;
- умеренную синхронность;
- стабильный режим;
- высокое качество данных.

Другая стратегия может требовать прямо противоположное.

Добавление новой стратегии не должно требовать переделки Маяка.

---

# 5. Торговая стратегия

## Роль

Торговая стратегия отвечает:

> **Есть ли сейчас конкретная торговая возможность по моим правилам?**

Она использует:

- собственную геометрию;
- собственные causal признаки;
- при необходимости оценку среды Диспетчера;
- собственный риск-контракт.

Стратегия сама решает, учитывать Диспетчер или нет.

Диспетчер не является обязательным сигналом Entry.

---

# 6. Entry

Entry отвечает только за:

- обнаружение торговой возможности;
- проверку собственных причинных условий;
- создание запроса на вход.

После подтверждённого fill Entry перестаёт владеть сделкой.

Entry не должен повторно определять логику Exit/Risk уже открытой позиции.

---

# 7. Execution

Execution отвечает за фактическое исполнение решения.

Биржа является источником истины по:

- фактическому avg fill;
- qty;
- order IDs;
- client IDs;
- позиции;
- stop;
- active orders;
- leverage;
- margin/position mode.

Execution обязан создавать долговечный handoff после fill.

Минимально:

```text
symbol
side
actual_avg_fill
actual_qty
fill_time
initial_stop
exchange_order_ids
client_order_ids
protection_ids
```

---

# 8. Risk

Risk отвечает:

> **Сколько система имеет право потерять?**

Risk не определяет Entry.

Risk не должен увеличивать допустимую денежную потерю из-за плеча.

Базовый принцип:

```text
денежный риск
=
размер позиции × расстояние до stop
+ комиссии
+ проскальзывание
+ другие реальные расходы
```

Не смешивать:

- движение цены в %;
- R;
- equity %;
- notional;
- margin;
- leverage.

---

# 9. Position Supervisor

После подтверждённого fill отдельный Position Supervisor наблюдает:

> **Что происходит с конкретной реальной позицией?**

Он может видеть:

- фактический fill;
- локальную causal структуру;
- поток;
- OI;
- стакан;
- состояние Маяка как внешний контекст.

Supervisor не должен становиться Entry.

Его наблюдение должно переживать restart/reconnect и опираться на реальную позицию биржи.

---

# 10. Exit

Exit отвечает:

> **Когда и как закрыть уже существующую позицию?**

Exit не должен заново определять Entry.

Будущие правила раннего закрытия, сопровождения, фиксации прибыли и защиты от общерыночного обвала должны исследоваться отдельно от Entry.

---

# 11. Биржа — источник живой истины

Для живой торговли локальное состояние не имеет приоритета над свежим exchange state.

После restart/reconnect система обязана сверять:

- реальные позиции;
- qty;
- avg fill;
- stops;
- active orders;
- order IDs;
- leverage;
- balance;
- margin/position mode.

Не открывать вторую позицию только потому, что локальная память считает рынок flat.

---

# 12. Fail-closed

Для обязательных живых данных:

```text
UNKNOWN != ZERO
NO DATA != NEUTRAL
STALE != SAFE
```

Если обязательное состояние неизвестно:

- WARMUP;
- WAITING;
- BLOCKED;
- ERROR;

в зависимости от слоя.

---

# 13. Research и Production

Исследование и реальная торговля разделены.

Research может:

- искать закономерности;
- сравнивать профили;
- строить контрфактические сценарии;
- оценивать полезность Маяка/Диспетчера.

Production содержит только причинную online-логику.

Запрещено переносить в live:

- будущие свечи;
- future-derived features;
- holdout-derived скрытые правила;
- исследовательские datasets как runtime dependency.

---

# 14. Жизненный цикл новой автоматизации

Любое новое торговое влияние проходит:

```text
RESEARCH
   ↓
SHADOW
   ↓
LIVE EQUIVALENCE
   ↓
MICRO_LIVE
   ↓
LIVE
```

Переход между стадиями — отдельное решение.

Новый аналитический слой не получает право торговать автоматически только потому, что технически установлен.

---

# 15. Почему статистика является частью архитектуры

Система должна развиваться не по ощущениям и не по нескольким ярким сделкам.

Каждая новая идея должна иметь достаточный причинный статистический след.

Поэтому:

> **сбор статистики — не дополнительная функция проекта, а обязательный инфраструктурный слой.**

Без него невозможно честно понять:

- что улучшилось;
- что ухудшилось;
- какой фильтр спас убыток;
- сколько хороших сделок он уничтожил;
- где работает конкретная стратегия;
- где она перестаёт работать;
- действительно ли новый слой создаёт положительную чистую экономику.

---

# 16. Главный принцип статистики

Не хранить только итог сделки.

Нужно сохранять:

> **что система знала в момент принятия решения.**

Это позволяет воспроизводить причинную историю.

# 23. Статистика неоткрытых сделок

Очень важно сохранять не только реальные сделки.

Если стратегия отклонила сигнал из-за:

- собственного правила;
- профиля среды;
- risk;
- отсутствия данных;

после факта research должен иметь возможность посмотреть дальнейшую causal price path.

Это необходимо для оценки:

> **стоимости отказа от хорошей сделки.**

---

# 24. Shadow / контрфактическая статистика

Если новый слой ещё не имеет торговых прав, он всё равно должен писать:

```text
что бы он рекомендовал
когда
почему
при каких данных
```

После факта можно сравнить с реальным исходом.

Но shadow recommendation не должна менять живую сделку.

---

# 25. Кластерная статистика

Отдельные сделки не всегда независимы.

Проект обязан уметь исследовать:

- несколько стопов в 5/15/30/60 минут;
- синхронные позиции;
- общерыночные события;
- portfolio crowding;
- общий directional exposure.

Это особенно важно для серийных убытков в одном рыночном событии.

---

# 26. Portfolio statistics

Signal replay не равен portfolio backtest.

Для портфельной оценки нужно учитывать:

- хронологию;
- одновременные позиции;
- капитал;
- margin;
- повторные Entry;
- one-position-per-symbol contract, если он принят;
- конфликты сигналов;
- correlation/crowding;
- fees/slippage/funding.

---

# 27. Статистика качества данных

Каждый серьёзный результат должен знать:

```text

какие отсутствовали
сколько данных было stale
coverage
missing periods
duplicates
clock problems
schema issues
```

Нельзя сравнивать два периода так, будто данные одинаковы, если в одном работал полноценный стакан, а в другом его не было.

# 29. Holdout и OOS

Discovery и подтверждение должны быть разделены.

Если holdout уже просмотрен:

> он больше не является чистым holdout для ретюнинга тех же правил.

Новые пороги после просмотра требуют новых unseen данных.

---

# 30. Статистика полезности фильтра

Любой будущий фильтр/Диспетчер/режим оценивается не только по спасённым убыткам.

Минимальная экономика:

```text
спасённые будущие убытки
-
потерянные хорошие сделки
-
потерянные восстановления
-
дополнительные комиссии
-
дополнительное проскальзывание
=
чистая ценность
```

---

# 31. Простая стратегия является benchmark

Более сложное правило должно доказать преимущество над заранее определённым простым benchmark с учётом:

- net PnL;
- PF;
- drawdown;
- trade count;
- cross-asset stability;
- concentration;
- operational complexity.

Небольшой прирост может не оправдывать усложнение системы.

---

# 32. Никакой автоматической самооптимизации live по результатам сделок

Результаты торговли идут:

```text
LIVE DATA
   ↓
STATISTICS
   ↓
RESEARCH
   ↓
NEW VERSION
   ↓
SHADOW
```

Запрещено:

```text
проиграли сделку
   ↓
автоматически изменить live Mayak/Dispatcher/Entry
```

без отдельного исследовательского и версионного цикла.

# 36. Настройки тоже являются статистикой

Нужно иметь append-only историю изменений параметров.

Не достаточно знать:

> какие настройки стоят сейчас.

Необходимо знать:

> какие настройки действовали в момент конкретного сигнала или сделки.

Поэтому каждое решение должно ссылаться на:

```text
settings_version
policy_version
```

# 37. Временная причинность

Любая статистика, используемая для оценки решения в момент T, должна быть доступна к T.

Запрещено связывать событие с будущим снимком.

Для внешних событий различать:

```text
event_time
published_at
received_at
used_at
```

---

# 38. Часы и задержки

При нескольких биржах измерение lead/lag возможно только при контроле времени.

Система должна знать:

- server clock drift;
- exchange timestamp;
- local receive time;
- transport delay where measurable.

Иначе межбиржевое «опережение» нельзя считать доказанным.

# 39. Интерфейс и аудит

UI показывает состояние системы, но не является скрытой стратегией.

Любой параметр UI, влияющий на торговое решение, должен:

- быть реальным runtime config;
- иметь audit trail;
- иметь version/history.

---

# 40. Разрешённые зависимости

Концептуально:

```text
MARKET SOURCES
      ↓
    MAYAK
      ↓
  DISPATCHER
      ↓
  STRATEGIES
      ↓
ENTRY / RISK / EXECUTION / EXIT
```

Supervisor может читать:

```text
exchange position
market data
Mayak context
```

Research может читать историю всех слоёв.

---

# 41. Запрещённые зависимости

Нельзя:

```text
Strategy result → Mayak classification
Position PnL → Mayak state
Dispatcher → Mayak mutation
Mayak → direct order
UI → hidden strategy mutation
Research dataset → live mandatory runtime dependency
Future outcome → past feature
```

---

# 42. Масштабирование проекта

Будущая архитектура должна позволять:

- много CEX;
- много DEX;
- много торговых стратегий;
- несколько аккаунтов;
- отдельные conservative/aggressive стратегии;
- shared Mayak;
- shared Dispatcher;
- независимые Risk contracts.

Но расширение не должно разрушать границы ответственности.

---

# 43. Главная метафора проекта

> **Маяк описывает море.**

> **Диспетчер объясняет, каким типам плавания это море подходит.**

> **Торговая стратегия выбирает маршрут и момент выхода из порта.**

> **Risk определяет допустимую цену ошибки.**

> **Execution управляет фактическими командами бирже.**

> **Position Supervisor наблюдает конкретный корабль после выхода.**

> **Статистика записывает весь путь так, чтобы завтра мы могли доказательно сделать систему лучше.**

---

# 44. Критерий хорошей архитектуры

Перед добавлением новой функции задать вопросы:

1. Какой слой обязан знать эту информацию?
2. Это наблюдение или торговое решение?
3. Не начинает ли один слой выполнять работу другого?
4. Есть ли причинный audit trail?
5. Сможем ли мы через месяц статистически доказать пользу изменения?
6. Можно ли воспроизвести решение по сохранённым версиям и данным?

Если ответов нет — изменение архитектурно не готово.

---

# 45. Изменение этого документа

`PROJECT_ARCHITECTURE_RU.md` является глобальным контрактом.

Фундаментальное изменение ролей слоёв требует:

- новой версии документа;
- явного описания причины;
- обновления `AGENTS.md`;
- проверки зависимых архитектурных документов.

Изменение этого файла не должно происходить скрытым hotfix.

# 46. Итог

Проект развивается не путём наращивания одного «умного бота».

Он развивается как система независимых специализированных слоёв:

```text
наблюдать
→ описывать среду
→ выбирать подходящую стратегию
→ принимать торговое решение
→ контролировать риск
→ исполнять
→ сопровождать
→ сохранять статистику
→ исследовать
→ выпускать новую версию
```

Основной долгосрочный актив проекта — не только код.

Это:

> **код + причинная статистическая история + воспроизводимость решений.**
